**贯穿案例 · 林小满**

网站上线第三周，一切顺利。直到某天，顾客群里有人问了一句："小满，我们的电话和地址存在你网站上，会不会泄露啊？"

林小满盯着这行字，后背发凉。她答不上来——她根本没想过这个问题。当天晚上她做了三件事：第一，把接短信通知的 API 密钥从代码里搬出来，放进环境变量；第二，给"看订单"的后台页面加了个简单的登录，不然谁猜到网址都能看顾客电话；第三，把这章的自查清单打印出来，贴在了烤箱旁边的墙上。

她说："以前觉得安全是程序员的事，现在明白了——**顾客把电话交给我，就是把信任交给我**。"

## 12.1 安全是底线，不是加分项

很多人觉得：我的网站这么小，谁会来搞我？

真相是：攻击你的人根本不认识你。网上有无数自动扫描的小程序，24 小时不停地敲各个网站的门，找没锁的、钥匙插在门上的。你的网站小，不代表门不用锁——**小偷撬的从来不是"值钱的门"，是"没锁的门"**。

安全这件事，和好吃不一样。面包好吃是加分项，安全是底线：好吃的面包出一次食品安全问题，店就没了；好用的网站出一次泄露，信任就没了。对林小满这种靠邻居信任吃饭的小店，信任就是一切。

好消息是：你不需要成为安全专家。你只需要做到本章这几件小事，就能挡住 99% 的麻烦。

## 12.2 登录：认出你是谁

**认证**（authentication）——人话：认出你是谁。就像你家店门上的锁，钥匙对上了才让进。

你的网站迟早会有"后台"：看订单、改价格、下架商品的页面。这个页面必须上锁。最简单的锁就是账号密码登录：只有你知道账号密码，只有你能进。

三个土规矩，照做就行：

1. **密码别用生日和 123456**。用一句你记得住、别人猜不到的话，比如"你家面包真香2026"。
2. **后台地址别太好猜**。别叫 `/admin` 这种全世界都知道的名字，换个只有你知道的。
3. **输错几次就锁一会儿**。很多登录工具自带这个功能，打开它——这是防"有人拿字典一个个试密码"的。

林小满的后台登录就是让 AI 加的，她只提了一个要求："账号密码只有我知道，输错 5 次就锁 10 分钟。"AI 十分钟搞定。她说："这比我家防盗门还让我安心。"

## 12.3 授权：不同的人看到不同的东西

**授权**（authorization）——人话：认出你是谁之后，决定你能干什么。进店的都是客人，但只有店员能进后厨。

以后你的网站可能会有两种人：顾客（下单）和你（管订单）。顾客只能看到自己的订单，你能看到所有订单、能改价格。这就是授权：**不同的人，看到不同的东西，能做不同的事**。

现在你的网站可能只有你一个人用，授权看起来多余。但记住这个概念，因为第 13 章收款、第 14 章做大之后，你一定会用到。到时候跟 AI 说一句话就行："顾客只能看自己的订单，管理员能看全部"——AI 听得懂。

## 12.4 钥匙放好：环境变量

每个网站都有几把"钥匙"：发短信通知的 API 密钥、支付的密钥、AI 接口的密钥。**API**（application programming interface）——人话：你的网站留给外部服务用的"专用窗口"，钥匙就是开这个窗口的凭证。

钥匙有三条铁律：

1. **不写进代码里**。代码会被复制、被传到 GitHub、被发给 AI 看——写进代码的钥匙，等于贴在电线杆上。
2. **放进环境变量**。**环境变量**——人话：专门放钥匙的抽屉，代码要用钥匙时去抽屉里拿，但钥匙本身不出现在代码里。在项目里就是一个叫 `.env` 的文件，里面写 `短信密钥=xxx` 这样的内容。
3. **`.env` 文件绝不传到网上**。GitHub 上公开的代码仓库里，绝不能出现这个文件。上传前检查一遍——这是本章最重要的一个动作。

第 2 章我们说过"AI 是搭档，不是保险箱"——这里再加一句：**问 AI 问题可以，贴钥匙不行**。你要 AI 帮你改发短信的代码，把密钥那一行涂掉再贴。钥匙一旦进了对话框，就等于告诉了全世界。

林小满现在养成了习惯：每次让 AI 改代码前，先搜一遍有没有密钥。她说："就像出门前摸一摸口袋，钥匙在不在。"

## 12.5 别把用户数据裸奔

你的订货系统里有什么？顾客的姓名、电话、取货时间。**这些不是"数据"，是别人交到你手里的隐私**。

三条规矩：

1. **最少收集**。下单需要电话，你就只收电话。别顺手收身份证、生日——你用不上，还担风险。记住：**你收集的每一项信息，都是一份责任**。
2. **别到处存**。顾客电话只存在该存的地方，别复制一份放表格里、又截图发到群里。林小满以前的习惯是把订单截图发到店员小群——现在改了，群里只发"3 号订单好了"，电话只在后台看。
3. **传输要加密**。人话：顾客填电话、你登录后台，这些页面地址必须是 `https://` 开头（带小锁头），不能是 `http://`。现在的部署平台（比如 Vercel）默认就给你配好，检查一下就行。

## 12.6 上线前安全自查清单

每次大更新上线前，花 10 分钟跑一遍这个清单：

- [ ] 后台页面不登录打不开（换个没登录过的浏览器试试）
- [ ] 代码里搜不到任何密钥（搜 `key`、`secret`、`password` 这几个词）
- [ ] `.env` 文件不在 GitHub 上（去你的代码仓库网页上看一眼）
- [ ] 网站地址是 `https://` 开头
- [ ] 只收集了必须要的信息
- [ ] 登录输错几次会被锁一会儿

林小满把这张清单贴在烤箱旁，每次更新完网站，烤面包的间隙就过一遍。她说："10 分钟，买个安心。"

## 本章要点

1. 安全是底线不是加分项：小网站也会被自动扫描盯上，锁好门就行。
2. 认证是认出你是谁（登录），授权是决定你能干什么（不同人不同权限）。
3. 钥匙三铁律：不写进代码、放进环境变量、`.env` 绝不上传；也不贴给 AI。
4. 用户数据是隐私：最少收集、别到处存、传输走 `https`。
5. 上线前花 10 分钟跑一遍自查清单。

## 动手 Kata

1. 在你的项目里搜 `key`、`secret`、`password`，看有没有密钥躺在代码里。
2. 把找到的密钥搬进 `.env` 文件，确认 `.env` 没有被传到 GitHub（去仓库网页上看一眼）。
3. 给你的后台管理页加上登录（直接跟 AI 说："加个登录页，账号密码只有我知道"）。
4. 换个没登录过的浏览器，试试不登录能不能打开后台。
5. 跑一遍 12.6 的自查清单，缺哪项补哪项。

## 翻车现场

老王（第 1 章里那个做了二手书 App 的程序员群友）这次又栽了。他图省事，把短信平台的 API 密钥直接写在代码里，传到了公开的 GitHub 仓库。三天后，短信平台账单来了：多了几千块钱——有扫描机器人在 GitHub 上专找这种泄露的密钥，拿去群发垃圾短信，花的全是他的钱。

他花了一整天换密钥、删记录、跟平台申诉。最后只说了一句："**密钥就是银行卡密码**，我居然把它贴在了电线杆上。"

教训：密钥不进代码、不进 Git、不进对话框。三条铁律，违反任何一条，账单都会教你做人。
