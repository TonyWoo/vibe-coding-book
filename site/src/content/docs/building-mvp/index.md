**贯穿案例 · 林小满**

蓝图画好了：4 个页面——首页、菜单、购物车、订单，外加一张功能清单。林小满把第 4 章的蓝图文档往 Cursor 里一贴，说："照这个做。"

三天后，她的电脑上真的跑起来一个网站：首页有她的店名和招牌面包，菜单页能按"面包 / 蛋糕 / 饮品"筛选，点"加入购物车"右上角数字会跳，购物车里填上名字电话、选好取货时间，一点提交——订单页里多了一条"待取货"。

她把链接发到顾客群。当晚 9 点，第一条真订单来了："王阿姨，碱水面包 ×2，明早 8 点取。"林小满盯着屏幕看了半天，差点哭出来——这不是演示，这是真生意。

这一章，讲的就是这三天里发生的事：怎么把蓝图变成一个能用的 MVP。

## 5.1 MVP：最小可用，不是最小能看

MVP 这三个字母，第一次见的人话解释：**Minimum Viable Product，最小可用产品**。注意，是"可用"，不是"能看"。

"能看"的意思是：页面漂漂亮亮，按钮一点，啥也没发生——那叫 PPT，不叫产品。"可用"的意思是：**核心流程能走通**。对林小满来说，核心流程就一条：客人选好东西 → 留下名字电话和取货时间 → 她收到订单。这条路通了，就是 MVP；这条路不通，页面再美也没用。

所以第一版的功能清单，林小满是拿着剪刀剪出来的：

- 留：首页（让人知道这是谁的店）、菜单（选商品）、购物车（确认要啥）、下单（留信息）、看订单（她备货用）。
- 剪：会员登录（先不记谁是谁）、在线支付（先到店付钱）、评价系统（先微信里夸）、优惠券（以后再说）。

记住这句大白话：**MVP 不是"功能最少"，是"离钱最近"**。凡是不能让客人更快下单的功能，第一版都不配上桌。

## 5.2 前后端分工：谁干什么

你会听到两个词：前端、后端。人话版：

- **前端**：客人眼睛看得到、手指点得到的部分——页面长啥样、按钮在哪、点一下发生什么。林小满的菜单页、购物车页，全是前端。
- **后端**：客人看不见、但离了它不行的部分——订单存哪、数据怎么算、跟外部服务打交道。

那 API 呢？API 就是前后端之间的"传话员"。前端说"我要下单"，API 把这句话翻译成后端听得懂的格式递过去，后端存好订单，再让 API 把"存好了"递回来。你可以把 API 理解成餐厅里的服务员：客人（前端）不进后厨（后端），有事叫服务员（API）。

好消息是：**第一版，你可以几乎不要后端**。订单存在哪？先存在客人的浏览器里（下一节讲）。商品数据从哪来？直接写死在代码里的一张表。没有服务器、没有数据库，网站照样能跑、照样能接单。等你订单多到浏览器装不下了，再请后端出场——那是第 7 章和第 11 章的事。

## 5.3 数据先记下来：localStorage 起步

"数据存在哪"听起来吓人，其实你每天都在用：微信聊天记录存在你手机里，备忘录存在你手机里——**浏览器也有这么个"小抽屉"，叫 localStorage**。

人话解释：localStorage 是浏览器自带的一个小本子，每个网站都有自己的一本，只能记文字（比如订单内容），关掉浏览器再打开，本子还在。容量不大，但记几百条订单绰绰有余。

林小满的第一版就是这么干的：客人一下单，订单就写进这个小本子；她打开"我的订单"页，网站就从小本子里把订单读出来列好。全程没经过任何服务器。

当然，小本子有三个毛病，你得心里有数：

1. **换台手机就没了**——本子跟着浏览器走，不跟着人走。
2. **只能记文字**——图片、文件塞不进去。
3. **不安全**——懂行的人能翻开看，所以别记密码、别记银行卡（第 12 章细讲）。

所以 localStorage 的定位是：**起步神器，不是终点**。第一版用它"先记下来"，等生意真做起来了，再搬进真正的数据库——到时候你会发现，因为第一版把"要记哪些东西"想清楚了，搬家特别顺利。

## 5.4 指挥 AI 搭出第一版

蓝图在手，工具就位（第 2 章选的 Cursor），开工。记住你的身份：**你不是写代码的，你是包工头**。包工头不搬砖，包工头派活、验收。

派活的正确姿势，一次只派一件：

1. **先搭架子**："照蓝图建 4 个页面：首页、菜单、购物车、订单，页面之间能互相跳转。"——先让路通。
2. **再填内容**："菜单页显示 12 个商品，分面包、蛋糕、饮品三类，数据先写死。"——先让货上架。
3. **然后走流程**："购物车能加减数量，能填名字、电话、取货时间，提交后在订单页能看到。"——再让钱能进来（先是信息流）。
4. **最后调样子**："整体用暖色，像面包房，手机上看着舒服。"——样子永远是最后一步。

每次派完活，验收三件事：**跑起来了吗？流程走得通吗？跟蓝图一致吗？** 通不过就打回去："购物车提交后订单页没显示，重做。"——别客气，AI 不玻璃心。

林小满的三天就是这么过的：第一天路通了，第二天货上架了，第三天流程走通了。她说，最大的体会是："我以前觉得做网站是'写'出来的，现在发现是'指挥'出来的。"

顺带一提，书里的示例项目"小满烘焙"（sample/ 目录）就是按这个顺序搭的：app/ 文件夹下 page.tsx 是首页，menu/、cart/、orders/ 三个文件夹各管一个页面——你对照着看，会很有感觉。

## 5.5 跑起来，发给真人用

网站在你电脑上跑起来，不叫上线，叫"自嗨"。**发给真人用，才叫 MVP 诞生**。

发之前，先自己当一回客人：拿手机打开（第 6 章会讲手机适配，这里先保证别错位），从头到尾下一个单——选商品、加购、填信息、提交、去订单页确认。**凡是你自己都走不顺的地方，客人一定走不顺**。

然后发到你的"种子用户"群——就是第 1 章里投过票、说"做好了第一个通知我"的那十几个人。配一句话："网站做好了，试试在线下单，取货时间自己选，有问题直接跟我说。"

林小满发出去的当晚，收到三条反馈：王阿姨说字太小（第二天调大）；老陈说取货时间只能选明天（加了"后天"选项）；女儿说："妈，你这网站真能用啊。"——**真人用的第一晚，胜过你自己琢磨一个月**。MVP 的"可用"二字，是用户盖的章，不是你自己封的。

## 本章要点

1. MVP 是"最小可用"，不是"最小能看"：核心流程走通才算数。
2. 前端是客人看得见的部分，后端是看不见的部分，API 是中间的传话员；第一版可以几乎不要后端。
3. 数据先用 localStorage 记下来：浏览器自带的小本子，够第一版用；换设备、记图片、安全性是它的三块短板，心里有数就行。
4. 你是包工头：一次派一件活——先搭架子，再填内容，然后走流程，最后调样子；每次验收"跑起来了吗、走得通吗、跟蓝图一致吗"。
5. 发给真人用才叫诞生；第一晚的用户反馈，胜过自己琢磨一个月。

## 动手 Kata

1. 对着你的蓝图，给 AI 派第一件活："建 N 个页面，页面之间能互相跳转。"验收：每个页面都能点进去。
2. 派第二件活：把核心内容填进去（商品、文章、信息——按你的项目来），数据先写死。
3. 走一遍核心流程：从进网站到完成"最小可用"的那个动作，全程录屏或截图，记下卡住的地方。
4. 发给 3 个真人用，收集原话反馈，修最疼的一个问题。

## 翻车现场

小李是程序员转行做独立开发，习惯了"大公司做派"。他的 MVP 做了两个月：用户系统、权限管理、日志、监控、单元测试覆盖率 80%——客人下单的流程反而还没调通。上线那天，他发了条朋友圈："历时 62 天，我的 SaaS 终于上线了！"评论区一片点赞，但没有一个人下单——因为下单按钮点进去是 404。

两个月后他才想明白：**他做的不是 MVP，是"最小能看的简历"**。MVP 的观众永远只有一个：愿意掏钱（或掏时间）的用户。用户不看你的测试覆盖率，用户只看"我能不能下单"。

教训：第一版只干"离钱最近"的事，其他的，都是以后的事。
